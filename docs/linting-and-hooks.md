# Linting & git hooks (SonarLint + EditorConfig + Husky)

This document covers the code-quality setup shared by the two .NET hosts: SonarLint/Sonar
analyzers, the `.editorconfig` that defines the code style (including **tabs, never spaces**),
and the Husky hooks that run before `git commit` and `git push`.

## 1. What is installed

| Tool | Where it lives | What it does |
| --- | --- | --- |
| **SonarLint** | Editor extension (`SonarSource.sonarlint-vscode`, or the Rider / Visual Studio plugin) | Shows Sonar findings while you type. |
| **SonarAnalyzer.CSharp** | `Directory.Build.props` (applies to every project) | The same Sonar rule engine as a Roslyn analyzer, so `dotnet build` reports the findings too. This is what makes the linter work in CI and in the hooks, not only in one person's IDE. |
| **`.editorconfig`** | Repository root | Single source of truth for formatting and analyzer severities. Read by VS, Rider, VS Code and `dotnet format`. |
| **Husky** | `.husky/` + dev dependency in `package.json` | Installs the git hooks when someone runs `npm install`. |
| **lint-staged** | dev dependency in `package.json` | Runs the formatter only on the C# files staged for the commit. |

Node.js is only used for the hook tooling — the application itself is .NET. Node `>= 20.17` is
required (see `engines` in `package.json`).

## 2. One-time setup

```bash
npm install
```

`npm install` runs the `prepare` script (`husky`), which points `core.hooksPath` at `.husky/_` and
activates the hooks for your clone. Check it worked with:

```bash
git config core.hooksPath   # → .husky/_
```

If hooks do not run (for example after deleting `node_modules`), run `npm run prepare` again.

### Editor setup

- **VS Code**: install the workspace recommendations (`SonarLint`, `C# Dev Kit`, `EditorConfig for
  VS Code`). `.vscode/extensions.json` lists them, and `.vscode/settings.json` already configures
  C# with tabs and format-on-save.
- **Rider / Visual Studio**: install the **SonarLint** plugin. Both read `.editorconfig`
  natively. The SonarAnalyzer NuGet package means their Error List / Problems view shows the same
  rules as the command-line build.

## 3. Tabs rule

`.editorconfig` sets, for every `*.cs` file:

```ini
[*.cs]
indent_style = tab
indent_size = tab
tab_width = 4
```

`dotnet format whitespace` uses that file, so formatting and this rule never drift apart. A file
is compliant when `git show HEAD:path/to/File.cs | grep -P '^    '` finds nothing (except inside
string literals, which the formatter never rewrites).

Other file types (JSON, YAML, Markdown, XML, project files) use spaces; YAML does not allow tabs.
Generated EF Core migrations are formatted with tabs too, but are exempt from the namespace-style
rule because EF would regenerate them in its own style.

> **Adding a migration:** EF writes `*.Designer.cs` and `AppDbContextModelSnapshot.cs` with an
> `<auto-generated>` header, and `dotnet format` skips auto-generated files. The migration body is
> formatted normally, but convert the Designer/snapshot file to tabs before committing (VS Code:
> *Convert Indentation to Tabs*). `dotnet format --verify-no-changes` does not catch these files.

## 4. Hooks

### `pre-commit` — format what you are committing

```
npx lint-staged --relative
```

`lint-staged` passes the staged C# files to
`dotnet format whitespace src/Nurtricenter.Api/Nurtricenter.Api.slnx --include <files>`, then
re-stages the formatted files. The `--relative` flag is required: `dotnet format --include`
does not match absolute paths.

If the formatter changes a file, the commit includes the corrected (tab-indented) version. If
`dotnet format` fails, the commit is aborted.

### `pre-push` — verify the whole solution

```
dotnet format whitespace ... --verify-no-changes   # tabs rule across the repo
dotnet build ...                                   # SonarAnalyzer runs here
dotnet test ...                                    # 299 tests, no external services
```

The push is aborted if any step fails. The build prints the Sonar findings as warnings; they do
not fail the build by themselves (`TreatWarningsAsErrors` is not enabled).

### Bypassing a hook

`git commit --no-verify` / `git push --no-verify` skip the hooks. Use only for emergencies: the
next push runs `dotnet format --verify-no-changes` and will fail if the code is not formatted.

## 5. Manual commands

| Command | Effect |
| --- | --- |
| `npm run format` | Formats the whole solution with tabs. |
| `npm run format:check` | Fails if any C# file needs formatting. |
| `npm run lint` | Builds the solution, showing Sonar findings. |
| `npm run lint:staged` | Runs the same formatter the `pre-commit` hook uses. |

Equivalent without npm:

```bash
dotnet format whitespace src/Nurtricenter.Api/Nurtricenter.Api.slnx
dotnet format whitespace src/Nurtricenter.Api/Nurtricenter.Api.slnx --verify-no-changes
dotnet build src/Nurtricenter.Api/Nurtricenter.Api.slnx
```

## 6. Changing the rules

- Formatting / indentation: edit the relevant section of `.editorconfig`.
- Analyzer severity: add `dotnet_diagnostic.<RULE_ID>.severity = none | suggestion | warning |
  error` under the appropriate glob. Example already in the file: `S6931` is disabled for
  `Endpoints/**` because those are `Ardalis.ApiEndpoints` classes, not MVC controllers, so the
  "add a controller route prefix" rule does not apply.
- Run `npm run format` after changing formatting rules, and commit the reformatted files.
